# Implementation Plan: Stale Flag Detection & Lifecycle Management

**Branch**: `015-stale-flag-management` | **Date**: 2026-08-08 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/015-stale-flag-management/spec.md`

## Summary

The platform will automatically detect and manage stale feature flags that have remained unchanged or fully rolled out for 30+ days. This involves tracking evaluation timestamps efficiently via in-memory aggregation, periodically scanning environments using a background worker to update a new `lifecycle_state` ENUM (`ACTIVE`, `STALE`, `DEPRECATED`, `ARCHIVED`), and exposing UX tools for Release Managers to safely archive dead flags, thereby excluding them from SDK streaming payloads and reducing technical debt.

## Technical Context

**Language/Version**: Go (Golang) 1.21+ (Backend) / TypeScript + React (Frontend)

**Primary Dependencies**: PostgreSQL (via lib/pq), Redis (optional for aggregation layer), Vite (Frontend)

**Storage**: PostgreSQL 16+

**Testing**: `go test` (Backend), Vitest/Jest (Frontend)

**Target Platform**: Linux containers (Backend), Modern Browsers (Frontend)

**Project Type**: Web Service + Single Page Application

**Performance Goals**: Sub-millisecond flag evaluation in SDKs MUST NOT be impacted by timestamp tracking. Timestamp writes must be batch-flushed to avoid DB lock contention.

**Constraints**: Must adhere to strict Environment Isolation.

**Scale/Scope**: Millions of SDK evaluations per minute mapped to timestamp aggregates; hundreds of flags scanned per background job tick.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- **I. API-First Contract Design**: API endpoints for lifecycle actions will be defined first.
- **II. Environment Isolation**: Lifecycle status is bound to `environment_flag_states`, not global flag logic. SDK payloads are filtered per-environment.
- **III. Governance by Default**: `ARCHIVE` and `DEPRECATE` actions will be gated by RBAC (Release Manager / Project Owner).
- **IV. Local Evaluation Performance (NON-NEGOTIABLE)**: `last_evaluated_at` updates will be performed asynchronously in the background. The synchronous evaluation path will not execute any SQL `UPDATE` statements. **PASSED**.
- **V. Test-First Quality Gates**: 80%+ backend coverage required for the new scanner service and async metric buffer.
- **VI. OpenFeature Interoperability**: Archiving a flag maps to OpenFeature "flag not found" / default fallback semantics.
- **VII. PII Protection & Compliance**: N/A for this feature.
- **VIII. Cloud-Native Portability**: Fully compatible.
